# OCR WebUI 产品 Roadmap

## 项目定位

**轻量、纯 CPU、自部署的 OCR webui，基于 RapidOCR (onnx) PP-OCRv6。**

核心价值：把不可编辑/搜索的图片、PDF，变成可编辑、可搜索、可导出的结构化文本。相对云端 OCR（百度/腾讯）的差异化：**数据不出本地、部署门槛低（纯 CPU）、可视化校对**。

## 能力边界（明确不做）

以下功能需要布局理解或大模型，纯 CPU 跑不动，偏离"轻量"定位，**明确划在边界外**：

- ❌ 表格结构识别（保留行列结构）— 需布局模型
- ❌ 字段提取（发票/身份证关键字段）— 需模板/布局理解
- ❌ GPU 模型（PaddleOCR-VL / vLLM 等）— 偏离纯 CPU 定位（上游代码保留，但不作为本项目主推）

## 核心约束

- **CPU 推理速度**：small 档，ORT ~4s/页、OpenVINO ~3s/页（23 行，Intel Xeon 8259CL 实测）。是物理约束，优化方向是"让等待可接受"（进度/异步/批量）+ 选对引擎（Intel 用 OpenVINO）。
- **同步架构瓶颈**：当前前端同步等 OCR 响应，导致超时/无进度/无批量。任务化是根本解法。

## 性能基准（Intel Xeon 8259CL，PP-OCRv6 small）

| 配置 | 23行 | 273行 | 51行 |
|---|---|---|---|
| ORT 4逻辑线程 | 5.67s | 8.79s | 3.93s |
| ORT 2物理线程 | 6.93s | 12.17s | 4.76s |
| OpenVINO 2线程 | 2.98s | 8.45s | 2.32s |
| **OpenVINO 4线程（默认）** | **3.19s** | **6.87s** | **2.26s** |

结论：Intel CPU 上 OpenVINO 比 ORT 快 22-47%，已设为 `docker-compose.rapidocr.yml` 默认。AMD CPU 应改回 `RAPIDOCR_ENGINE_TYPE=onnxruntime`。线程数用默认（`os.cpu_count()` 逻辑核），不要手动设物理核（实测逻辑核更快）。OpenVINO 首次推理有编译开销（慢），第二次起才体现优势。

## P0 — 地基（先做，其他依赖）

### P0-1 OpenResty 超时 ✅
- **问题**：多页 PDF 推理累积超 60s，OpenResty 默认 `proxy_read_timeout` 导致 504 中断。
- **方案**：server 块加 `proxy_read_timeout 300s`。
- **状态**：已完成。

### P0-2 启动预热
- **问题**：onnxruntime 首次推理某尺寸图时含形状推断 + 内存 arena 分配，多约 1s/页。bench 预热后这 1s 消失。
- **方案**：adapter `lifespan` 启动时用典型 A4 尺寸（@200DPI ≈ 1654×2335）跑一次 `engine(dummy_image)`，预热形状。
- **依赖**：无。

### P0-3 访问控制
- **问题**：当前无认证，公网部署任何人能白嫖 CPU、查看任务历史。
- **方案**：单用户密码 + 会话（复用现有 `PANDOCR_API_TOKEN` 机制扩展为登录态）。轻量门禁，不做多用户。
- **依赖**：无。多用户隔离（P2-6）依赖此项。

### P0-4 定位 + 文档更新
- **问题**：README 写"四个模型"（过时，实际五个含 rapid）；开源用户困惑项目定位；部署文档缺 Linux 一键指引。
- **方案**：README 明确"RapidOCR CPU 为主推"，修正模型数，补 `docker-compose.rapidocr.yml` 部署章节。
- **依赖**：无。

## P1 — 核心体验（性价比最高的改造）

### P1-1 任务化架构 ⭐ 分水岭
- **问题**：同步请求套慢 OCR → 超时/无进度/无批量/失败重来。这是体验差的根因。
- **方案**：上传 → 立即返回 task_id → 后台 worker 异步处理 → 前端轮询/SSE 进度 → 完成通知。基础设施已有（task 存储、batch 机制），改请求流程。
- **价值**：一次解决超时、进度、批量、可靠性。是"工具"变"产品"的关键。
- **依赖**：无（基础设施已有）。

### P1-2 进度反馈 + 可取消
- **问题**：用户盯着转圈，不知道进度、无法取消。
- **方案**：进度条 + "第 N/M 页" + 基于已处理页耗时预估剩余时间 + 取消按钮（中断 worker）。
- **依赖**：P1-1（任务化）。

### P1-3 全屏拖拽 + Ctrl+V 粘贴
- **问题**：拖入视觉反馈只在 drop-zone（用户不知能拖别处）；截图 OCR 要先生成文件，摩擦大。
- **方案**：`document.dragenter` 全屏蒙层"松开即可上传"；`document.paste` 读剪贴板图片直接 OCR。
- **依赖**：无。低成本快赢。

### P1-4 置信度标红
- **问题**：`rec_scores` 拿到了但没利用，用户不知哪里可能错。
- **方案**：低置信度（如 <0.6）文字行标黄/红，一眼定位需校对处。
- **依赖**：无。OCR 产品差异化。

### P1-5 键盘导航文字框
- **问题**：逐行校对要鼠标点，低效。
- **方案**：Tab/↑↓ 切换文字框、Enter 进编辑、Ctrl+Enter 确认。
- **依赖**：无。

### P1-6 批量上传
- **问题**：一次只能传一个文件，多文件要手动重复。
- **方案**：多文件拖入/选择 → 排队 → 逐个（或有限并行）处理。
- **依赖**：P1-1（任务化后自然支持队列）。

### P1-7 PDF 页范围选择
- **问题**：100 页 PDF 只想 OCR 第 5-10 页，现在必须全跑。
- **方案**：前端加页范围输入（如"5-10, 15"），后端 `prepare_images` 按 slice 渲染指定页。
- **依赖**：无。大文档刚需。

### P1-8 OCR 语种选择
- **问题**：RapidOCR 支持 `lang_type: ch/en/multi`，但硬编码中文，英文/混排文档效果打折。
- **方案**：前端语种下拉，adapter `params` 传 `Det.lang_type`/`Rec.lang_type`。
- **依赖**：无。能力已有未暴露。

### P1-9 结果统计
- **问题**：识别完不知整体质量（要不要细校）。
- **方案**：结果区顶部信息条 — 总字数、平均置信度、耗时、页数。数据都有（rec_scores/elapse）。
- **依赖**：无。纯前端。

### P1-10 存储管理
- **问题**：task 持久化但无清理，长期撑爆磁盘。
- **方案**：后端清理端点（按时间/数量删）+ 前端管理入口（查看占用、清理旧任务、设保留期）。
- **依赖**：无。

## P2 — 增强（按需，不阻塞主线）

### P2-1 任务历史管理
- **方案**：任务列表/搜索/筛选/重导出/删除 UI（task 已持久化，补管理界面）。

### P2-2 档位切换
- **方案**：前端选 small/medium/tiny。adapter 改惰性多引擎缓存（首次切档位下载，之后秒切）。
- **依赖**：基础稳定后做。

### P2-3 隐私控制 + 卖点
- **方案**：处理完即删源文件、可配保留期、日志不记 OCR 内容。作为核心卖点写进 README（相对云端 OCR 的差异化）。

### P2-4 API 文档
- **方案**：OpenAPI 已有，补 API 使用文档 + curl/Python 示例。让项目从"工具"升级成"服务"。

### P2-5 导出格式扩展
- **方案**：DOCX（可编辑排版）、可搜索 PDF（原图层 + 不可见文字层，扫描件归档刚需）。

### P2-6 多用户数据隔离
- **方案**：注册/登录/每用户任务隔离。重型，仅真有多人场景才做。
- **依赖**：P0-3（访问控制）。

### P2-7 骨架屏 / Toast / 空状态
- **方案**：加载骨架屏替代转圈、Toast 操作反馈、首次进入空状态引导（"拖拽或粘贴开始"）。

### P2-8 移动端适配
- **方案**：窄屏/拍照 OCR 场景的布局验证与修复。

### P2-9 图片旋转
- **方案**：前端 canvas 旋转（90°/自由角度），旋转后再送 OCR。解决拍照歪斜（rapid 无文档矫正）。

### P2-10 撤销/批量替换
- **方案**：校对模块加撤销栈、全局查找替换（系统性识别错误如"己/已"）。
