# 现状问题分析报告（第一性原理）

> 性质：分析记录。所有声明经代码核验，见文末交叉验证记录。

## 〇、结论摘要

schema 归位重构消除了旧审计的根因（前端拥有领域模型），项目当前没有「致命级」问题。但用第一性原理重新审视，剩下的问题可以归为一个张力：

**这是一个单用户、低资源、长寿命的自维护工具，却持续为一个不再运行的产品形态（多模型 GPU 部署）支付复杂度、攻击面和认知税。**

最大的五项发现（按 代价×发生概率 排序）：

1. **GPU 遗产税**：server.py 约 960 行（~24%）+ 4 个 Dockerfile + 2 个 adapter + compose + pipeline 配置服务于 CPU 部署永远不运行的模型；前端还保留两条浏览器编排路径。
2. **任务文件并发写是"类"问题不是"实例"问题**：上次修了 /process 的一个实例，但多写入方共享同一临时文件的机制仍在；且新加的 PATCH 没有活跃作业防护（新引入的洞）。
3. **部署攻击面继承自上游**：CPU compose 把 Docker socket 挂进 web 容器（收益极小）；登录端点无限速；上轮 SECURITY.md 有一处我写错的事实（已修正）。
4. **前端 35 个模块级全局 + replaceTask 浅合并**：在"服务端拥有 schema"之后，内存镜像与服务器文档的偏差风险反而更值得管理。
5. **35 处 patch.object 把测试锁死在 server 门面上**：这是新出现的元问题——它让 P4（拆模块）的实际成本高于单纯搬代码。

## 一、第一性原理框架

这个项目的本质：**一个人为自己的文档工作流搭的、跑在弱 CPU VPS 上的、要用很多年的工具**。对这类系统，评判标准不是功能丰富度或架构时髦度，而是四个量：

| 标准 | 含义 | 当前状态 |
|---|---|---|
| 变更成本 | 每个未来功能的边际代价 | 中——schema 归位后数据层干净了，但单文件与双编排路径仍在 |
| 失败代价 | 数据损坏/丢失/被入侵的代价×概率 | 数据：有一个未封死的并发类问题；安全：三个部署面问题 |
| 资源上限 | 2C4G 级 VPS 的内存/磁盘/CPU 边界 | 引擎缓存内存占用至今未实测（唯一硬缺口） |
| 认知负担 | 单人维护时"改之前要理解多少" | server.py 3953 行、app.js 5873 行、5 模型概念面 |

以下按此框架展开。

## 二、发现一（结构）：GPU 遗产税 —— 最大的持续成本

**事实**：
- server.py 第 187–1150 行（约 960 行）：模型目录解析、Docker Engine 客户端、容器编排、健康检查、模型切换/部署/无限后端切换——全部服务于"多模型 GPU 热切换"这个上游产品形态。
- 仓库内为不运行的模型保留：`Dockerfile.ocr`、`Dockerfile.ovisocr2`、`Dockerfile.unlimited-ocr`、`Dockerfile.unlimited-ocr-sglang`、`unlimited_ocr_adapter.py`、`ovisocr2_adapter.py`、`docker-compose.yml`（多模型 GPU 版）、pipeline 配置。
- 前端仍保留两条浏览器编排路径（Unlimited-OCR 的 SSE 流式循环、PaddleOCR-VL 的阻塞循环）——它们是"前端拥有数据"时代的最后领土：本地重建 markdown、维护 images 映射、PUT 全量任务。任务处理因此存在**三种模式**（服务端队列 / 浏览器阻塞 / 浏览器流式）。

**第一性原理分析**：你的部署是 `PANDOCR_MODEL_CATALOG=pp-ocrv6-rapid` 单模型。上述代码在这个部署上的运行时贡献≈0，但贡献了：①每次读 server.py 的导航成本；②测试面（35 处 patch 中相当部分 patch 的是这套机制的属性）；③P4 拆模块时必须为它做架构决策（拆成 model_runtime 模块？还是删掉？）；④上游取材时的持续干扰（上游的更新大头恰恰落在这里，这也是为什么上游更新对我们价值趋零）。

**但注意反面**：这套遗产是"取材关系"的物理载体——删掉它等于宣告彻底独立。这是一个**产品决策**而非技术决策：三根支柱（纯 CPU/队列/校对）已经与上游分道，遗产是拖累还是期权，取决于你是否还想在未来某天切回 GPU 路径。

**建议**：不急于删。给 P4 加一个前置决策："拆模块时，GPU 编排层拆成独立的 `model_runtime.py` 并用 feature flag 圈起来"——圈地比删除便宜，保留期权，同时把主路径（CPU 单模型）的导航成本降下来。若一年内无 GPU 需求，再删。

## 三、发现二（数据）：并发写类问题 + PATCH 防护缺失

**事实**：
1. `write_task_bundle` 的写入方有五个（worker 的每批写入、PUT 纠正、PATCH、/process、启动恢复），全部通过"写 `.tmp` 再 `os.replace`"落盘。Windows 下两个线程同时打开**同一个** `task.json.tmp` 会交错写入产生损坏 JSON——这是上次实测复现的机制（Extra data）。/process 已改为"无变更不写"堵住了一个实例，但**类**未封死。
2. 新增的 `PATCH /api/tasks/{id}` 没有活跃作业检查：对一个正在跑的任务发 `{"reset": true}` 会在 worker 追加结果的同刻清空 ocrResults 并删除 pages 目录，两个写入方随即竞争。前端不会这么调，但 API 层面是敞的（api.md 公开了这个端点）。

**分析**：对单用户工具，这属于低概率×高代价（纠正过的校对数据是无价的）。修法便宜且是"封类"而非"堵实例"：
- 每任务一把 `asyncio.Lock`，所有 `write_task_bundle` 调用方持有（约 10 处调用点收敛到一个入口函数）；
- PATCH/PUT 在 `TASK_JOBS` 显示 queued/processing 或存在 processing 批次时返回 409。

**规模边界顺带记录**（当前无害，不行动）：每批完成重写整个 result.json + 前端每批拉全量详情，是 O(N²) 的写/传模式；400 页 PDF 大约是 1MB×400 次重写与全量下载——在 VPS 上仍在秒级，但这是未来"大文档慢"的第一嫌疑。

## 四、发现三（安全）：部署面三件事

1. **Docker socket 挂进了 web 容器**（`docker-compose.rapidocr.yml:68`，`MODEL_CONTROL=docker`，继承自上游）。收益：UI 能 inspect/restart rapidocr 容器。代价：web 进程任何 RCE = 宿主机 root。而它的功能收益几乎可被替代——`MODEL_CONTROL=none` 时状态检查退化为 HTTP health probe（代码已支持），引擎档位切换走 HTTP 不走 Docker。**这是当前部署里收益/风险比最差的一行配置**。上轮我在 SECURITY.md 里凭假设写成"未挂 socket、MODEL_CONTROL=none"，是事实错误，本轮已修正（这也是给"报告必须核验"的注脚）。
2. **登录端点无限速**：`/api/auth/login` 单密码、无锁定、无限流。公网 VPS + 30 天会话意味着攻击面长期存在。建议：应用层加一个简单的失败计数（内存即可，单用户不需要完整限流中间件），或在 OpenResty 层做 `limit_req`。
3. **会话寿命名不副实**：文档说 30 天，实际 `AUTH_SESSIONS` 在内存里——进程重启全部失效。这不是漏洞，是"文档承诺 > 实际行为"的小偏差，重启后需重新输密码而已。记录即可。

## 五、发现四（前端）：状态与镜像偏差

**事实**：模块级可变全局约 35 个（比旧审计的 25 还多几个）；`replaceTask` 仍是浅合并——服务器删除的字段会在内存镜像里永生。

**分析**：schema 归位后这个问题**性质变了**：以前全局态是"唯一事实"，现在内存任务只是服务器文档的镜像 + 会话 UI 态（jobState 等）两种东西混居。浅合并的偏差风险从"温床"升级为"镜像必然漂移"（例如服务端某天不再返回某字段，前端合并后仍拿旧值做决策）。P5（容器化）依然可以暂缓，但有一个 30 分钟级的中途站：**把 `replaceTask` 改为"以服务器文档为准 + 白名单保留 UI 态"的替换式合并**——单独修这个陷阱，不必等全面容器化。另外测试现在是 12 个冒烟级用例对 5873 行代码——harness 已立，覆盖率是后续按需生长的事，不必刻意补。

## 六、发现五（元问题）：测试与 server 门面的耦合

**事实**：test_server.py 有 35 处 `patch.object(server, ...)`（httpx.AsyncClient、acquire_ocr_slot、task_model_runner、MODEL_CATALOG_IDS……）。

**分析**：这些 patch 把"server.py 单门面"从选择变成了**被测试固化的契约**。将来做 P4 时，每拆一个函数出去，就要么改 patch 目标、要么让 server 再导出符号（门面化，拆了等于没拆）。这就是 P4 实际成本高于"搬代码"的原因。建议 P4 动工时把"patch 目标跟着被测单元走"作为拆分验收标准之一，避免拆出一个空壳门面。

## 七、非问题清单（防止过度工程）

| 方面 | 为什么不是问题 |
|---|---|
| FIFO 单 worker 吞吐 | 单 CPU 部署的正确设计，不是缺陷 |
| 每批落盘 + 重启恢复 | 持久性设计正确，且是并发写问题的补偿机制 |
| 撤销单级/会话级 | 用户已论证是伪需求 |
| 存储只手工清理 | 单用户 + 有 cleanup API，自动清理是伪需求 |
| 错误码/i18n 层次 | 上一轮审计确认做对了 |
| OpenAPI 快照手工生成 | check-local 已做 stale 校验，风险被闭环 |
| O(N²) 写传模式 | 当前规模无害（见三节边界记录），到痛点再改增量写 |
| README 截图旧 | 门面问题，等 UI 稳定 |

## 八、建议与优先级

| # | 行动 | 量级 | 类型 |
|---|---|---|---|
| 1 | 任务写锁（每任务 asyncio.Lock 收敛写入入口）+ PATCH/PUT 活跃作业 409 | 半天 | 修数据类问题 |
| 2 | 部署决策：去 Docker socket（改 `MODEL_CONTROL=none` + 删挂载）或明确保留理由；登录失败限速 | 半小时~1 小时 | 安全，收益/成本最高 |
| 3 | `replaceTask` 改替换式合并（服务器文档为准 + UI 态白名单） | 30 分钟~2 小时 | 修镜像偏差陷阱 |
| 4 | 实测三档引擎缓存内存占用（openvino 默认下 LRU 3） | 1 小时 | 补事实缺口，决定是否要 TTL |
| 5 | P4 前置决策：GPU 编排层"圈地"（独立模块 + flag）还是删除 | 决策 + 1-2 天 | 结构 |
| 6 | P4 拆模块（含 patch 目标迁移） | 1-2 天 | 结构，触发条件不变 |

1–4 互相独立、都是小项，可随下次顺手做；5 是产品决策（删 or 留），建议在想清楚"是否还可能回 GPU"之后定；6 维持既有触发条件。
